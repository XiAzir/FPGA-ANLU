# Native 1080p JPEG + YUV420 block-buffer throughput harness

This harness drives the C34 complete JPEG front end and native IDCT output into `idct_yuv420_block_buffer`. It excludes HDMI, SDRAM, audio, and FFT. It does not edit the C34 core or the existing small JPEG testbench.

## Prepared fixtures

`prepare_native1080.py` verified the source MJP index and extracted:

| Fixture | Source frame | JPEG bytes | SHA256 |
| --- | ---: | ---: | --- |
| `frame000` | 0 | 61,664 | `d9c9d36910e6ba1d4f7f5dc21ceae791b378f55981f2be283a8ad9cebe75127a` |
| `frame108_max` | 108, largest | 69,028 | `f9b1bde6865ffd9ff94691f2d6ea4e6d6304796aa82afdb15bd050141df10089` |

Each fixture has `.jpg` and `$readmemh` `.hex` files in this directory; `fixtures.json` records source frame, byte length, payload word count, source word count, and SHA256. The byte source sends every payload word with `last=0`, then a separate empty tail word (`data=0`, `strb=0000`, `last=1`) as required by `jpeg_input`.

## Harness checks

`tb_native1080.v` checks per-block IDCT index uniqueness and ID stability, exactly 48,960 real blocks and 3,133,440 real samples, one EOF block, and exactly 783,360 output word writes. It rejects any word address outside 0–783,359 or duplicate address, then checks that every address was written once. With `word_ready` stalled one cycle per 13, it asserts that valid/address/data stay stable during each stall.

After a successful run, the bench writes address-ordered YUV420 tiled output as little-endian 32-bit words. The runner checks the 3,133,440-byte output size and records CRC32 plus fixture identity in a summary JSON. The address layout follows the block buffer: Y plane first, then Cb and Cr planes, each in padded 16×16 MCU tile order.

## Prepared commands

Prepare/recheck the fixture files:

```powershell
python development/video34_work/native1080/prepare_native1080.py
```

Compile only (no VVP run):

```powershell
python development/video34_work/native1080/run_native1080.py --fixture frame000 --mode decode
python development/video34_work/native1080/run_native1080.py --fixture frame108_max --mode service
```

After the root agent releases long simulation, add `--run` to a selected command. `decode` supplies one accepted 32-bit input word per cycle. `service` models the conservative 1.22 MB/s input service at 100 MHz using 328 cycles per 32-bit word. `WORD_STALL_PERIOD=13` gives the output writer regular backpressure; override with `--word-stall-period 1` for continuous output readiness.

Both requested variants have been compile-checked with Icarus. No long VVP has been run with the corrected framing. The harness watchdog uses a conservative 180 cycles/block envelope; `--stop-cycles` can override it. For diagnosis, `--diagnostics` emits pipeline/queue snapshots every 100,000 cycles, and `--stop-cycles 8400000` reproduces the prior frame0 stop point with the end-state snapshot. The snapshot includes source progress, last input/native/word cycles, MCU state/geometry, IDCT descriptor/input-RAM state, and buffer banks.

The compile-only VVP image is regenerated by the runner for each command; VVP remains unstarted until `--run` is supplied. Before any full 1080p VVP, the corrected source framing was verified on the existing 16×16 blocks JPEG: 6 real blocks, 384 samples, one EOF block, all 96 output addresses, PASS at 1,262 cycles. The original 1080p failure is preserved and classified as `INVALID_FIXTURE_LAST_WORD_TRUNCATION` in `frame000_decode.invalid.log`; it asserted `last` on the final payload word and lost the final three byte lanes.

## Cycle and memory estimates

The harness expects 120 MCU columns × 68 padded MCU rows × 6 blocks = 48,960 blocks; 3,133,440 8-bit samples; 783,360 32-bit writes; and 3,133,440 raw bytes. For `frame000`, the current estimator gives 4,107,316 cycles, about 41.1 ms at 100 MHz. For the maximum frame at the modeled 1.22 MB/s input service, it gives 5,710,296 cycles, about 57.1 ms at 100 MHz. These are planning estimates; only VVP can establish observed cycles.

The address coverage map uses under 1 MB of logical state, the by-address 32-bit output capture uses about 3.1 MB logical storage, and the raw file is 3.13 MB. Four-state simulator overhead and actual VVP wall time remain to be measured. This is a software timing model, not a board or real SDRAM service result.
